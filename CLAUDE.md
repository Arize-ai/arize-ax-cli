# CLAUDE.md

Guidance for Claude Code and other AI coding agents working in this repository.

`ax` is the official Arize CLI: a [Typer](https://typer.tiangolo.com/) app that
wraps the `arize` Python SDK. It owns argument parsing, configuration profiles,
error presentation, and output formatting — not API communication.

Read [DEVELOPMENT.md](DEVELOPMENT.md) for the full architecture tour. This file
covers the conventions that are easy to violate and the checks that must pass.

## Quick start

```bash
uv venv --python 3.13 .venv
uv pip install -e ".[dev]"

task lint         # ruff format . && ruff check --fix .
task type-check   # mypy, strict config, must be clean
task test         # pytest with coverage
task all          # all three, in the order CI runs them
```

`task all` must pass before any change is proposed. CI runs the `ci-*` variants
(`ci-format` checks formatting rather than applying it), so a change that only
passes after `--fix` still fails CI. Integration tests are excluded by default
and need a real `ARIZE_API_KEY`; do not try to run them without one.

## Repository facts worth knowing up front

- **This repo is a Copybara export of an internal monorepo.** Commit history is
  squashed imports, so `git log` and `git blame` are not useful for tracing a
  change back to its review.
- **`CHANGELOG.md` is generated by release-please. Never edit it by hand.**
  Describe user-facing changes in the PR body instead.
- **`src/arize/_generated/`** (when vendored) is generated OpenAPI code and is
  excluded from linting. Do not edit generated code; change the caller instead.
- Python 3.11+ is required. `pyproject.toml` is the single source of truth for
  dependencies, lint rules, and task definitions.

## Layering

```
cli.py  →  commands/  →  core/  →  utils/  →  arize SDK
```

- `commands/` — one module per noun (`datasets.py`, `projects.py`, ...). Holds
  Typer options, input validation, and user-facing messages.
- `core/` — CLI-specific logic: `@handle_errors`, output formatting, exception
  classes, the error formatter. Knows about SDK responses and CLI concerns.
- `utils/` — generic helpers with no CLI-specific knowledge. A util must not
  import from `commands/`, and should not print: take an `on_progress` or
  `on_retry` callback and let the command own the console. `utils/batching.py`
  is the reference example.

If a helper needs to know about SDK error shapes it belongs in `core/`; if it
would work unchanged in any Python program it belongs in `utils/`.

## Writing a command

Every command follows the same shape. Copy an existing one rather than
inventing a variant.

```python
@app.command("append")
@handle_errors
def append_examples(
    name_or_id: Annotated[str, typer.Argument(help="Dataset name or ID")],
    space: Annotated[str | None, typer.Option("--space", "-s", help="...")] = None,
    output: Annotated[str, typer.Option("--output", "-o", help="...")] = "",
    verbose: Annotated[bool, typer.Option("--verbose", "-v", help="...")] = False,
) -> None:
    """One-line summary used as the command's help text."""
    setup_logging(verbose)
    client, config = make_client()
    output_format, output_file = parse_output_option(
        output if output else config.output.format
    )

    try:
        with spinner("Appending examples", success_msg="Appended examples"):
            result = client.datasets.append_examples(...)
    except Exception as e:
        raise APIError(f"Failed to append examples: {e}") from e
    else:
        output_data(result, format_type=output_format, output_file=output_file)
```

Rules this encodes:

- `@app.command("kebab-case")` then `@handle_errors`, in that order.
- `Annotated[...]` for every parameter, with an explicit help string.
- `setup_logging(verbose)` first, then `make_client()`.
- Wrap SDK calls and re-raise as the matching `AxError` subclass with `from e`.
  Never call `sys.exit()` or `typer.Exit()` directly from a command body.
- Put the success path in the `else:` branch — ruff's `TRY300` enforces it.
- Print results through `output_data()`, never `print()`.
- Reuse `--space/-s`, `--output/-o`, `--verbose/-v`, `--file/-f`, `--json`,
  `--limit/-l`, `--cursor/-c` with their established meanings.

## Errors

Raise the subclass from `core/exceptions.py` that carries the right exit code:
`UsageError` (2), `AuthenticationError` (3), `APIError` (4), `FileIOError` (5),
`ConfigError` (1). For bad user input, prefer `typer.BadParameter` — Typer
formats and exits on its own.

**The message you pass to an `AxError` is not always what the user sees.** When
`core/error_formatter.py` finds an SDK `ApiException` anywhere in the
`__cause__` chain, it renders that API failure and discards the wrapper's text.
So any context that cannot be recovered from the API error — how far a partial
operation got, what to run to resume — must be printed to the console *before*
the raise. `_report_partial_upload()` in `commands/datasets.py` is the pattern.

Do not classify errors by matching substrings in exception text. Use
`parse_exception()` from `core/error_formatter.py`, which walks the cause chain
and understands `ApiException`, gRPC/Flight errors, and pydantic validation
errors. `utils/batching.http_status()` wraps it for status-code checks.

## Tests

Tests live in `tests/`, mirroring `src/ax/`. Command tests use the shared
fixtures in `tests/commands/conftest.py` (`cli_runner`, `mock_client`,
`patch_config_and_client`) and invoke through Typer's `CliRunner` — they assert
on exit codes, on the SDK calls that were made, and on what reached the user,
never on internals.

- Name the behavior, not the mechanics: `test_rejected_payload_is_not_retried`,
  not `test_append_2`.
- Assert the exit code on every failure path. A command that reports trouble
  but exits 0 is a bug.
- Never sleep in a test. Inject the clock — `send_batches(sleep=...)` — or patch
  it (`patch("ax.utils.batching.time.sleep")`).
- Class-per-command-or-concern, one docstring line each, matching the file.

## Style

- Ruff, line length 80 (E501 only fires past 110), Google-style docstrings,
  full type annotations. `from __future__ import annotations` at the top of
  modules, with typing-only imports inside `if TYPE_CHECKING:`.
- `# noqa` needs a reason on the same line or just above, and must name a rule
  that actually fires — `RUF100` fails the build on an unused directive. If a
  rule is wrong for a whole category of files, add a `per-file-ignores` entry
  with a comment rather than scattering directives.
- Comments should explain why, not restate the code. The interesting comments
  in this repo mark non-obvious constraints (why a payload is pinned to one
  version, why a fallback exists); match that bar.

## Changing behavior users already depend on

Command flags and output shapes are a public contract.

- Adding a flag is fine; changing what an existing invocation does is not.
  Default a new behavior so that a payload or input which worked before takes
  the same code path it took before.
- When a new default could be wrong for someone, give them the way back. The
  batching flags do this with `--batch-size 0`, which restores the original
  single-request behavior exactly.
- Update `README.md` (user-facing flags and examples) and `DEVELOPMENT.md`
  (new modules, architecture notes) in the same change.
